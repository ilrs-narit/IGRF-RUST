# ร่างออกแบบ Buildroot สำหรับ IGRF-RUST

สถานะ: ผู้ใช้ยืนยันแบบเบื้องต้นตาม Q34 แล้ว อยู่ระหว่างตรวจความเข้ากันได้ทางเทคนิค ยังไม่เริ่ม implementation หรือ build image

## ข้อกำหนดที่ยืนยันแล้ว

- เป้าหมาย: เปิดเครื่องเข้า IGRF-RUST ทันที และสร้าง OS image ซ้ำจากเวอร์ชันที่กำหนดได้
- รุ่นแรก: เครื่องต้นแบบในห้องทดลอง เพื่อทดสอบหน้าจอและอุปกรณ์จริง
- ฮาร์ดแวร์: Raspberry Pi 4 (BCM2711) กับจอสัมผัส 1024×600 — เปลี่ยนจาก Pi 5 ตาม [ADR 0003](adr/0003-pi4-kiosk-platform.md)
- การต่อจอ: HDMI สำหรับภาพ และ USB สำหรับสัมผัส; ยังไม่ระบุรุ่นจอ
- สื่อบูตเครื่องต้นแบบ: microSD เพื่อเขียน image และสลับการ์ดทดสอบได้ง่าย
- ความจุ microSD สำหรับต้นแบบ: 32 GB หรือมากกว่า; ยังไม่สรุปขนาดพาร์ทิชันจนกว่าจะประเมินขนาดระบบจริง
- การสร้าง image: สร้างบนคอมพิวเตอร์ Linux แล้วนำไปเขียน microSD
- การสร้างซ้ำ: ตรึงซอร์ส dependencies และสภาพแวดล้อม build ให้สร้างระบบเวอร์ชันเดิมได้ พร้อมบันทึกเวอร์ชันและ checksum ของแต่ละ image; รุ่นแรกไม่กำหนดให้ image เหมือนกันทุกไบต์
- การแยกพื้นที่: OS อ่านอย่างเดียว และมีพื้นที่เขียนแยกสำหรับค่าตั้งเครื่อง ฐานข้อมูล logs และเครือข่ายที่จำไว้; ต้องจัดตำแหน่งข้อมูลเขียนของแต่ละบริการและทดสอบจริง
- รุ่นจอ: ยังไม่ทราบ ให้ดำเนินการออกแบบเบื้องต้นได้ โดยค้างการยืนยันไดรเวอร์สัมผัสและโหมดภาพจนทราบรุ่นและทดสอบเครื่องจริง
- ข้อมูลถาวร: เก็บค่าตั้งเครื่อง ฐานข้อมูลดาวเทียม และ CSV logs ข้ามการรีบูต; การเขียน image ใหม่ต้องสำรองและนำกลับ ส่วนไฟดับเป็นไปตามเงื่อนไขด้านล่าง
- USB flash drive: เสียบแล้วต้องปรากฏในแอปสำหรับนำเข้า/ส่งออกไฟล์ พร้อมวิธีถอดอย่างปลอดภัย; คำสั่งถอดอยู่ในหน้าตั้งค่าหรือบริเวณสถานะตามแนวทาง UI ที่เลือก โดยกลไก mount ยังต้องยืนยัน
- ระบบไฟล์ของ USB flash drive: รองรับ FAT32 และ exFAT สำหรับนำเข้า/ส่งออกไฟล์
- เครือข่าย: รองรับ LAN และให้ผู้ใช้เลือกเครือข่าย Wi-Fi แล้วเชื่อมต่อจากหน้าจอแอป รวมถึงกรอกรหัสผ่านด้วยคีย์บอร์ดสัมผัส; มีอินเทอร์เน็ตเป็นบางครั้ง แต่ต้องเปิดแอปและใช้ข้อมูลที่เก็บไว้ได้เมื่อออฟไลน์
- Wi-Fi: รองรับเครือข่ายทั่วไปหรือฮอตสปอตมือถือที่ใช้ชื่อเครือข่ายและรหัสผ่าน พร้อมจำเครือข่ายเพื่อเชื่อมต่อใหม่
- หน้าจอ: เพิ่มการเลือก Wi-Fi ตั้งเวลา ถอด USB อย่างปลอดภัย และสถานะพื้นที่ logs ในหน้าตั้งค่าเดิมและบริเวณแสดงสถานะ โดยคงหน้าควบคุมหลัก
- ระบบแสดงผลรุ่นแรก: คง X11 และคีย์บอร์ด Onboard เป็นแนวทางหลักเพื่อลดการเปลี่ยนโค้ดหน้าจอ; ยังต้องยืนยันการแพ็ก dependencies และทดสอบบน Buildroot จริง
- การดูแลเครื่อง: เปิด SSH ผ่าน LAN โดยยืนยันตัวตนด้วยกุญแจ SSH ของผู้ดูแล
- เวลาเครื่อง: เมื่อเปิดเครื่องออฟไลน์และเวลายังไม่ถูกต้อง ให้ผู้ใช้ตรวจและตั้งเวลาก่อนเริ่มงานที่ใช้เวลา และซิงก์เวลาเมื่อมีเครือข่าย; ยังต้องกำหนดวิธีตรวจความน่าเชื่อถือของเวลาและการจัดการเมื่อเวลาถูกปรับระหว่างทำงาน
- การตั้งเวลาด้วยผู้ใช้: อนุญาตเฉพาะเมื่อหยุดงานที่ใช้เวลาแล้ว พร้อมแสดงสถานะซิงก์เวลา; นโยบายการปรับเวลาจากการซิงก์อัตโนมัติระหว่างทำงานยังต้องออกแบบ
- เมื่อแอปปิดตัวผิดพลาด: เปิดใหม่อัตโนมัติในสถานะหยุด ไม่กลับมาควบคุมเอง และจำกัดการลองซ้ำเมื่อผิดพลาดต่อเนื่อง; การเปิดแอปใหม่ไม่ใช่กลไกตัดกำลังขดลวด
- การทดสอบต่อเนื่อง: ผ่าน 72 ชั่วโมงก่อน แล้วทดสอบต่อ 30 วัน พร้อมแยกทดสอบ USB หลุด พื้นที่เต็ม และการกู้คืน โดยยังไม่จ่ายกำลังให้ขดลวด

- การอัปเดตรุ่นต้นแบบ: สำรองข้อมูลออกก่อน เขียน OS image ใหม่ลง microSD แล้วนำข้อมูลกลับ; ยังต้องกำหนดขั้นตอนสำรองและตรวจสอบการกู้คืน
- การเก็บ CSV logs (แก้ไขตามคำตอบ Q28 แทน Q14–Q15): ต้องเก็บต่อเนื่องหลายวันถึงหลายเดือน ไม่ใช้เพดาน 1 GiB เพื่อลบประวัติอัตโนมัติ ผู้ใช้จะนำ USB flash drive มาให้บันทึกเมื่อพื้นที่ไม่พอ
- การใช้ USB สำหรับ logs: เปลี่ยนไปบันทึกไฟล์ใหม่ลง USB โดยตรง และเก็บไฟล์เดิมบน microSD
- การเลือก USB สำหรับบันทึก: ผู้ใช้เลือกไดรฟ์แล้วกดใช้บันทึก ระบบปิดไฟล์เดิมและเริ่มไฟล์ใหม่บน USB ที่เลือก; การเสียบไดรฟ์เพียงอย่างเดียวไม่เปลี่ยนปลายทางบันทึก
- เมื่อบันทึก logs ต่อไม่ได้เพราะพื้นที่หมดหรือ USB หลุด: แจ้งเตือนและสั่งหยุดการทดลองผ่านกลไกหยุดปกติ ไม่เริ่มต่อเองจนผู้ใช้แก้ไขและสั่งเริ่ม; ต้องทดสอบเส้นทางนี้ และไม่ถือว่าการส่งคำสั่งหยุดรับประกันการตัดกำลังเมื่อการสื่อสารกับตัวควบคุมขาดหาย
- เมื่อไฟดับระหว่างบันทึก: ยอมเสียข้อมูลล่าสุดที่ยังเขียนไม่เสร็จ แต่ต้องตรวจพบข้อมูลเสียและมีวิธีกู้คืนค่าตั้งเครื่อง; วิธีตรวจสอบ สำรอง และกู้คืนยังต้องออกแบบและทดสอบ
- เมื่อค่าตั้งเครื่องเสียตอนเปิดแอป: เปิดหน้ากู้คืนในสถานะหยุด ให้ผู้ใช้เลือกค่าตั้งเครื่องสำรองที่ตรวจสอบแล้วก่อนเริ่มควบคุม
- คงหน้าจอเดิม รวมคีย์บอร์ดสัมผัส การตั้งค่า LAN และการเลือกไฟล์
- ทดสอบ image โดยไม่จ่ายกำลังให้ขดลวด ต้องกำหนดระบบตัดกำลังก่อนเริ่มทดสอบที่จ่ายกำลังจริง


## ภาพระบบเบื้องต้นที่ยืนยันแล้ว

ผู้ใช้ยืนยันแนวทางนี้แล้ว รายละเอียดแพ็กเกจและค่าคอนฟิกยังต้องตรวจสอบ ส่วนนี้ไม่ใช่ผลการ build หรือผลทดสอบ

- เก็บ defconfig, board configuration, root filesystem overlay และแพ็กเกจแอปใน BR2_EXTERNAL ของโปรเจกต์ ตรึง Buildroot และซอร์สที่ใช้สร้างแยกจาก output ของการ build
- ใช้ toolchain ของระบบที่เลือกสร้างแอปจาก Cargo.lock ไม่ใช้ binary release ที่สร้างสำหรับ Ubuntu/Pi OS โดยถือว่าเข้ากันได้ทันที ข้อมูลจาก crate ที่ resolve อยู่ระบุ Rust ขั้นต่ำ 1.95; ต้องตรวจความเข้ากันได้กับ Buildroot รุ่นที่จะเลือก
- ใช้ systemd สำหรับลำดับเริ่มบริการ การเปิดแอปใหม่แบบจำกัดครั้ง และบริการเวลา โดยให้แอปทำงานด้วยบัญชีเฉพาะที่ไม่ใช่ root
- เริ่มแอปเมื่อพื้นที่ข้อมูลและ X11/session D-Bus พร้อม ไม่รออินเทอร์เน็ต ใช้ X11, Mesa และ Onboard ตามแนวทางที่เลือก; ต้องพิสูจน์ dependency ของ Onboard และตัวเลือกไฟล์ก่อนสรุปรายการแพ็กเกจ
- ใช้ root filesystem อ่านอย่างเดียว ข้อมูลถาวรบน /data และข้อมูลชั่วคราวบน tmpfs ให้ working directory ของแอปอยู่บนพื้นที่ข้อมูลเพื่อรองรับพาธไฟล์เดิม พร้อมจัดพื้นที่ถาวรให้ NetworkManager และ SSH host keys
- ใช้ NetworkManager ต่อจากแนวทางเดิม เพิ่มการเลือก Wi-Fi ผ่านงานเบื้องหลัง และจำกัดสิทธิ์การเปลี่ยนเครือข่าย เวลา และถอด USB เฉพาะการดำเนินการที่จำเป็น
- ให้บริการระบบจัดการ mount USB ในพาธที่แอปมองเห็น ผู้ใช้เลือกปลายทาง logs เอง ก่อนถอดไดรฟ์ที่กำลังบันทึกต้องปิดการเขียนให้สำเร็จและ unmount; ถ้าขั้นตอนใดล้มเหลวต้องไม่แสดงว่าถอดได้แล้ว
- แบ่ง logs เป็นไฟล์ต่อเนื่องเพื่อรองรับการใช้งานยาวและ FAT32 โดยไม่ลบประวัติอัตโนมัติ แสดงพื้นที่ว่างและปลายทางปัจจุบัน ตรวจข้อผิดพลาดจากการเขียนจริง และสั่งหยุดตามข้อกำหนดเมื่อบันทึกต่อไม่ได้
- ขั้นตอนสำรองก่อนเขียน image ใหม่ต้องหยุดการเขียนข้อมูลหรือใช้วิธีสำรองฐานข้อมูลที่ได้ snapshot สอดคล้องกัน แล้วตรวจการนำกลับได้จริง ไม่คัดลอกเฉพาะไฟล์ฐานข้อมูลที่กำลังใช้ WAL โดยละเลยข้อมูลที่ยังไม่รวมกลับ

## เกณฑ์ทดสอบต้นแบบ

1. บูตจาก microSD เข้าแอปในสถานะหยุด ใช้จอสัมผัส คีย์บอร์ด และตัวเลือกไฟล์ได้ รวมถึงเมื่อไม่มีอินเทอร์เน็ต
2. ค่าตั้งเครื่อง ฐานข้อมูล logs และ Wi-Fi ที่จำไว้ยังอยู่หลังรีบูต และ OS ยังคงอ่านอย่างเดียว
3. เลือก USB FAT32/exFAT เพื่อบันทึกได้ ไฟล์เดิมบน microSD ยังคงอยู่ และถอด USB อย่างปลอดภัยได้เมื่อเลิกใช้
4. จำลองพื้นที่เต็มและ USB หลุดแล้วแอปแจ้งเตือน สั่งหยุด และไม่เริ่มการทดลองใหม่เอง
5. แอปปิดตัวผิดพลาดแล้วเปิดใหม่ในสถานะหยุด และหยุดลองซ้ำเมื่อผิดพลาดต่อเนื่องตามนโยบายที่กำหนด
6. ตั้งเวลาเองได้เมื่อหยุดงานที่ใช้เวลาเท่านั้น แสดงสถานะซิงก์เวลา และตรวจสอบพฤติกรรมเมื่อเวลาเปลี่ยน
7. ตรวจพบค่าตั้งเครื่องเสีย เข้าหน้ากู้คืน และเลือกสำเนาที่ตรวจสอบแล้วได้ ทดสอบสำรองและนำกลับหลังเขียน image ใหม่
8. ทดสอบต่อเนื่อง 72 ชั่วโมงก่อน แล้วต่อ 30 วัน โดยตรวจความต่อเนื่องของ logs การใช้หน่วยความจำ และพื้นที่ข้อมูล; การทดสอบความขัดข้องแยกจากช่วงทดสอบต่อเนื่อง

ยังไม่ได้ดำเนินการทดสอบเหล่านี้ และผลการทดสอบโดยไม่จ่ายกำลังไม่ใช่การรับรองการควบคุมขดลวดจริง

## ลำดับพิสูจน์แบบก่อนสร้าง image เต็ม

1. ตรวจซอร์สของ release ที่จะตรึงและ dependencies ของ toolchain/Onboard ให้ครบ พร้อม hash ของแหล่งที่มา
2. ทดลอง build และเปิด X11 + Onboard + แอป + file dialog บน Pi 4 โดยยังไม่จ่ายกำลังขดลวด ก่อนเพิ่มความสามารถใหม่ทั้งหมด
3. เชื่อมพื้นที่ข้อมูลถาวรและสิทธิ์ของบริการ แล้วเพิ่ม Wi-Fi เวลา USB และการจัดการ logs ตามข้อกำหนด
4. ทดสอบการกู้คืนและความขัดข้อง ก่อนเริ่มทดสอบต่อเนื่อง 72 ชั่วโมงและ 30 วัน

ค่าปฏิบัติการ เช่น จำนวนครั้ง restart, ขนาดไฟล์ log ต่อส่วน, พื้นที่สำรอง และขนาดพาร์ทิชัน ต้องระบุใน implementation และตรวจด้วยการทดสอบ ไม่ถือว่าผู้ใช้ได้เลือกตัวเลขเหล่านี้แล้ว
